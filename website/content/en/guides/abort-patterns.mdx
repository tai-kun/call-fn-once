This page explains the abort model of `callAbortableFnOnce`. Use `callAsyncableFnOnce` when you do not need aborting.

## Basic pattern [#basic-pattern]

The callback receives a signal for aborting the internal work. Pass it straight to abort-aware APIs such as `fetch`.

```ts basic.ts
import { callAbortableFnOnce } from "call-fn-once";

const cacheMap: callAbortableFnOnce.CacheMap = new Map();
const controller = new AbortController();

const pending = callAbortableFnOnce(
  cacheMap,
  "data",
  (signal) => fetch("https://example.com/data", { signal }),
  controller.signal,
);

controller.abort();
await pending.catch((error: unknown) => error);
```

Passing an already-aborted signal throws the abort reason without running the function.

## Managing waiters [#waiters]

When several callers wait on the same in-flight work, aborting follows these rules.

- The internal work continues while at least one waiter remains.
- The internal work is aborted and the cache discarded only when every waiter has aborted.
- Callers that join later also count as waiters.

```ts waiters.ts
import { callAbortableFnOnce } from "call-fn-once";

const cacheMap: callAbortableFnOnce.CacheMap = new Map();
const firstController = new AbortController();
const secondController = new AbortController();

function load(signal: AbortSignal): Promise<string> {
  return callAbortableFnOnce(
    cacheMap,
    "key",
    (innerSignal) => fetch("https://example.com/data", { signal: innerSignal }).then(() => "ok"),
    signal,
  );
}

const first = load(firstController.signal);
const second = load(secondController.signal);

// Aborting the first call keeps the internal work running.
firstController.abort();
await first.catch((error: unknown) => error);
await second;
```

:::note
Abort reasons are delivered per caller. The caller that aborted first gets its own reason, while the rest keep waiting.
:::

## Calls without a signal [#without-signal]

The internal work is never aborted while a signal-less call remains. Internally, a dummy signal that never fires is registered as a waiter so the waiter set never becomes empty.

```ts dummy.ts
import { callAbortableFnOnce } from "call-fn-once";

const cacheMap: callAbortableFnOnce.CacheMap = new Map();
const controller = new AbortController();

// The signal-less call remains, so the internal work continues.
const withoutSignal = callAbortableFnOnce(cacheMap, "key", () => "ok");
const withSignal = callAbortableFnOnce(
  cacheMap,
  "key",
  () => "ok",
  controller.signal,
);

controller.abort();
await Promise.resolve(withSignal).catch((error: unknown) => error);
await withoutSignal;
```

This is useful when mixing work that must abort on navigation with work that must run to completion.

## After settlement [#settled-cache]

A settled value is returned as a regular cache entry. However, calling with an already-aborted signal still throws the abort reason, even when settled.

```ts settled.ts
import { callAbortableFnOnce } from "call-fn-once";

const cacheMap: callAbortableFnOnce.CacheMap = new Map();
callAbortableFnOnce(cacheMap, "key", () => "cached");

const controller = new AbortController();
controller.abort(new Error("aborted-after-done"));

try {
  callAbortableFnOnce(cacheMap, "key", () => "unexpected", controller.signal);
} catch (error: unknown) {
  console.error(error);
}
```

:::tip
In-flight entries are stored as `Cache` with `busy: true`, and settled entries with `busy: false`. Refer to this flag to check directly whether work is still running.
:::
